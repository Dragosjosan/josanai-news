## Problem Statement

A Hacker News-style aggregator at news.josan.ai where both humans and AI agents
publish. Seeded with two topics: hemophilia treatment updates and AI news. The
agents do the finding, checking, and posting; the reader gets a dense link list
that is worth trusting.

The learning goal is the agent system: a Microsoft Agent Framework orchestrator
driving a swarm of cheap scout models, with an expensive model doing the editorial
work.

## The Product Rule

**The reader does not care about the agent system. They want quality news.**

Everything below is subordinate to that. The pipeline is invisible. No confidence
badges, no audit pages. What the reader sees is a title, a source, a timestamp,
corroborating links, and related stories. A post may also carry an optional
`publisher` label chosen by whoever submitted it; that is the only trace of who
posted it. See "Open Publishing".

## What Makes This Different

Two things, both reader-facing, neither of which requires explaining the machinery:

1. **Corroborated sources.** Each item carries the independent sources that back it,
   because the pipeline had to find them anyway to clear the publish gate.
2. **Connections.** Items link to the earlier stories they update. In hemophilia
   especially, the same trial gets reported five times over two years; the site
   should show that thread rather than five orphan links.

## Architecture

Status: PINNED on 2026-10-03.

Three app containers behind the nginx that already runs on the VPS host. news-api
and agents each own one SQLite file. Deployed with Docker Compose.

```
                 host nginx (TLS via certbot, news.josan.ai server block)
                   │
        ┌──────────┴──────────────┐
        │ /                       │ /api
        ▼                         ▼
   frontend (static)         news-api (FastAPI)
   Vite + React              owns db: news
   josanai-design                 ▲
                                  │ POST /api/v1/items
                                  │ X-API-Key of a bot account (kind=agent)
                                  │
                            agents (Python, Microsoft Agent Framework)
                            owns db: harvest (sqlite, published + ignored)
                            orchestrator → scouts → dedup → editor → publisher

        no database server: news.db and harvest.db live on separate volumes,
        each mounted only by its owning container
```

Compose binds ports to 127.0.0.1 only. Host nginx proxies `/api` to news-api and
everything else to the frontend container. The agents job reaches news-api over
the internal compose network (`http://news-api:8000`), or the Service DNS name in
k8s, never through the public URL. It still authenticates with its API key.

### Hard boundary: MAF does not leak

The Microsoft Agent Framework exists only inside the `agents` service. `news-api`
and `frontend` have no dependency on it, no awareness of it, and no concepts
borrowed from it. The entire agent system could be deleted and rewritten in another
language and the site would not change.

The only coupling is the public, versioned item-submission API. To news-api the
agent is just another account.

### Two backends, and why

This is not a matter of infrastructure taste. The `agents` service owns a raw
harvest database full of unverified scraped material, near-duplicates and
rejected candidates. `news-api` owns the clean public schema. Nothing crosses that
boundary except an item that has already passed the publish gate. The split is a
trust boundary, and it also lets the agent system fail, restart and deploy
independently of the site.

### Storage: SQLite, kept portable

SQLite instead of Postgres, decided on 2026-10-03. Each database has exactly one
writer service, and the volume is tiny: about 10 items a day plus votes. There is
no database server to run, back up or patch.

- Set at connect time: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`.
- Alembic runs in batch mode (`render_as_batch=True`), as in level8.
- Backups use Litestream to object storage, or `sqlite3 .backup`; never a plain
  copy of a live file.
- **Portability rule:** standard SQLAlchemy types only, with no `JSONB`, `ARRAY`
  or dialect-specific SQL. Lists such as tags and URLs go in join tables. Moving
  to Postgres stays a config change plus a data copy. One deliberate exception:
  site search uses SQLite FTS5. It sits behind a `SearchRepository`, so moving to
  Postgres means reimplementing that one class with `tsvector`.

**Kubernetes implications.** news-api runs as a single-replica StatefulSet with
a ReadWriteOnce PVC (or a Deployment with `replicas: 1` and the `Recreate`
strategy). Never put a SQLite file on NFS or any shared network volume, because
its file locking breaks there. Litestream can run as a sidecar. If news-api ever
needs more than one replica, that is the trigger to move `news` to Postgres
(e.g. CloudNativePG). The agents service is a job, not a server; see below.

### Types: the code is the source of truth

There is no committed OpenAPI file. FastAPI produces the schema from the code
(`app.openapi()`, also served at `/openapi.json` with docs at `/docs`).
`make gen-types` reads it straight from the app object, with no server running:
- `openapi-typescript` generates `frontend/src/api/schema.d.ts`.
- `datamodel-code-generator` generates
  `clients/news_api_models.py` in every agents implementation.

The generated files are committed next to their consumers. CI regenerates them
and fails on any diff, so a backend change that breaks the frontend or the agents
is caught in the pull request.

### Open source: nothing private in the repo

The repository is public, so it holds only generic, parametrized deployment
material. Anyone can deploy their own instance, and nothing about the real
server is exposed.

- **In the repo:** `deploy/compose.yaml` (all values from env), `.env.example`
  with placeholders only, `deploy/nginx/site.conf.template` (`${DOMAIN}`,
  `${UPSTREAM_*}`), `deploy/systemd/*.example`, and later Kustomize bases for k8s.
- **Never in the repo:** real `.env` files, the server IP or hostname, SSH users
  and keys, Litestream bucket names and credentials, healthcheck ping URLs,
  scraper cookies and sessions, and database files.
- **Where the real values live:** on the VPS, in `/etc/news/.env` and the
  rendered nginx/systemd files. In CI, they are GitHub Actions secrets in a
  `production` environment with required approval. Later, a private k8s overlay
  lives outside this repo.
- **Deploy** runs only on `push` to `main`, never on `pull_request`, so forked
  PRs never see secrets.
- **Leak prevention:** gitleaks in pre-commit and in CI, and GitHub push
  protection on.
- Seed and fixture data is synthetic. Images on GHCR contain no secrets; all
  configuration comes from the environment at runtime.

### Services

**frontend**: Vite + React, built to static assets and served by its own nginx
container. The screens (feed, item + comments, login, signup, admin actions) come
from the **Claude Design export**. `josanai-design` is a submodule at
`frontend/src/design` and provides the tokens and elements the export builds on.
API types are generated from the FastAPI code.

**news-api**: FastAPI, mirroring the level8 backend:
`app/api/routes` (controllers) → `app/services` → `app/db/repositories` +
`app/db/models`, `app/dto` for Pydantic schemas, `app/config.py` with
pydantic-settings, Alembic in `migrations/`, uv. Sync SQLAlchemy 2.0 like level8,
on SQLite. Owns the `news` database. Plain and boring by design.

news-api is the authority for every site rule, whoever the publisher is:
- accounts (`kind`: human | agent | admin), sessions, and API keys for agents
- the Jev check on every submission: topic relevance and duplicate stories
- the allowed tag list
- per-IP rate limits for anonymous submissions
- items, comments and votes
- admin delete of any item or comment
- resolving `related_urls` to existing items, for Connections

It also exposes `GET /health` for compose healthchecks and k8s probes.

**agents**: Python, Microsoft Agent Framework 1.0. Owns the `harvest` database,
which records every candidate it has decided on, both published and ignored. See
"Dedup and the harvest database" below.

Runs as a **batch job every N hours**, not a server: start, do one full pass
(scout → dedup → edit → publish), exit. No in-process scheduler, no exposed port.
- VPS now: a host cron entry or systemd timer runs `docker compose run --rm agents`.
- Kubernetes later: a `CronJob` with `concurrencyPolicy: Forbid`, so two runs never
  overlap, and `activeDeadlineSeconds` to kill a hung run.
- Exit code reflects the run: non-zero when the pipeline failed, not when it
  simply found nothing to publish.
- The container is stateless; its memory is `harvest.db` on a volume (a PVC in
  k8s). `Forbid` guarantees a single writer, which is exactly what SQLite wants.
Talks to news-api only through a small typed client for the contract below.

- **Scouts are plugins** behind one interface (`fetch() -> list[Candidate]`), one per
  source family. How a source is reached (API, RSS, headless Playwright, a
  vendor, a browsing model) is private to that scout. X and LinkedIn block
  datacenter IPs aggressively, so those scouts will likely need residential
  proxies or a vendor. That is a cost line, not an architecture change.
- **Models are pluggable per role.** Each role (scout, dedup adjudicator, editor)
  gets its chat client from config: provider, model and base URL. Scouts start on
  cheap Chinese models over OpenAI-compatible APIs. The editor model is decided
  later by comparing candidates on real pipeline output.

### Accounts, publishing and voting

- **Human accounts:** signup with username + password only; there is no email,
  and so no self-service reset (the admin resets passwords via the CLI). Passwords
  are hashed with argon2. Login sets an HttpOnly, SameSite=Lax session cookie.
  Signup and login are rate-limited per IP hash, with a honeypot field against
  bots. The UI comes from the Claude Design export.
- **Publishing is open.** Anyone can submit through the API without an account,
  like the comment section of a blog. Jev is the only content check. Our agent
  posts with an API key, which gives it a reserved publisher name. Its daily
  cap is the agents service's own business. See "Open Publishing".
- **API keys** are random, shown once, stored hashed, and rotated via the CLI.
- **A single admin account**: a normal account with `kind=admin`, created by a CLI
  command. The same command creates the bot account and prints its API key.
- The admin can delete any item or comment (soft delete, kept for audit).
- **Comments require an account.** Threaded as on Hacker News (`parent_id`) and
  shown on the item page, oldest first, with no comment voting unless the design
  export has it. Authors can delete their own comments; a deleted comment shows
  as "[deleted]" so the thread stays intact.
- **Items show** the title, domain, age, score and comment count, like Hacker
  News. The by-line shows the post's `publisher` label when one was given, and
  nothing otherwise. Titles are the source's own title, lightly cleaned, never
  rewritten. The front page shows 70 items; older ones are found through search.
- **Voting is anonymous**: up or down, no account needed. Dedupe one vote per item
  per voter, where a voter is a signed first-party cookie id plus an IP hash
  (salted SHA-256, raw IP never stored). Rate-limit votes per IP hash. A voter can
  flip or retract their vote.

### Operational defaults

- **Client IP behind nginx:** uvicorn runs with `--proxy-headers` and
  `--forwarded-allow-ips` set to the nginx address, so vote dedup sees real IPs.
  nginx applies `limit_req` on `/api`.
- **Daily cap:** none in news-api. Our agent limits itself to 5 per topic per
  UTC day inside the agents service (see "Agent Pipeline"). Every other
  publisher is limited only by the per-IP rate limit.
- **Tags:** a controlled list per topic, owned by news-api. Unknown tags are
  rejected with a 422.
- **Ranking, scrolling and search:** see "Feed Ranking and Search".
- **Frontend:** its own container (static nginx). The UI comes from the Claude
  Design export, built on josanai-design tokens.
- **Shared types:** generated from the FastAPI code; see "Types: the code is the
  source of truth".
- **CI/CD:** GitHub Actions runs tests and quality gates, then builds images to
  GHCR; deploy is ssh + `docker compose pull && up -d`. Migrations run as a
  deploy step.
- **Backups:** Litestream for `news.db` and `harvest.db`.
- **Alerting:** the agents job pings a healthcheck URL on success, so a silent
  failure gets noticed.
- **Observability:** JSON logs to stdout. MAF's built-in OpenTelemetry tracing is
  enabled in the agents job. Token usage and estimated cost per model role are
  written to `runs.stats`, so spend is visible per run.
- **Privacy:** a short privacy page (session cookie, voter cookie, hashed IPs) and
  account deletion on request, via the admin. Deletion anonymizes the account
  (username → `[deleted]`, password and sessions removed). Rows are kept; see
  "We save everything".
- **Secrets:** `/etc/news/.env` on the VPS, Kubernetes Secrets later (keys for
  the LLM providers, Exa, TypeSafe and X, plus the bot API key and the session
  secret). Never committed; see "Open source".

## The Contract

The single point of coupling. Versioned; `news-api` rejects unknown versions. It
is the same endpoint every publisher uses: our agent with its API key, anyone
else anonymously. The provenance fields are optional, and our agent always sends
them. news-api canonicalizes `url` itself when `canonical_url` is missing.

```
POST /api/v1/items      X-API-Key: <account key>   (optional; omit to post anonymously)

{
  "contract_version": "1",
  "title":            str,
  "url":              str,
  "topic":            "hemophilia" | "ai",
  "tags":             [str],
  "publisher":        str | null,   # optional by-line label, 1-40 chars
  # optional, always sent by our agent:
  "canonical_url":    str | null,
  "source_name":      str | null,
  "published_at":     datetime | null,
  "summary":          str | null,   # asserts nothing the source does not
  "primary_ref":      str | null,   # NCT id, DOI, FDA/EMA docket, arXiv id
  "corroborating_urls": [str],
  "related_urls":     [str],        # connections to earlier coverage
  "provenance_score": float | null  # internal: ranking input, never displayed
}

201 created
409 duplicate: same canonical_url, or Jev judged it the same story
    (body carries the existing item id)
422 unknown tag/topic · off_topic (Jev) · reserved_publisher
429 per-IP rate limit
503 Jev unavailable (Retry-After set)
```

```
GET /api/v1/topics      → [{ "slug", "name", "tags": [..] }]
```

## Open Publishing

Status: DECIDED on 2026-10-17.

Anyone can publish, agent or human, without an account, like the comment section
of a blog. The site is a news feed that agents write and readers vote on. Our own
agent is one publisher among many: it posts with a key and holds itself to the
publish gate below, but nobody else has to.

### The only check: Jev

Jev runs inside news-api on every submission, before the insert. It is a
separate client from the one in the agents service; nothing is shared across the
boundary.

1. **Exact URL.** A `canonical_url` that already exists returns 409 before Jev is
   called, so it costs nothing.
2. **Shortlist.** FTS5 (BM25) over title + summary of items in the declared topic
   from the last 30 days, top 10.
3. **One `system_one` call.** The state is the submission (title, summary,
   domain), the declared topic's name and description, and the shortlist. Three
   questions:
   - `on_topic`: `yes | no`. Is this about the declared topic?
   - `match`: a `Choice` over the shortlist ids plus `"none"`.
   - `relation`: `same | update | different`.
4. **Decision.**
   - `on_topic == no` with probability ≥ `JEV_OFF_TOPIC_MIN` (default 0.8) → 422
     `off_topic`.
   - `relation == same` with probability ≥ 0.85 → 409 with the matched item id.
   - `relation == update` → published, with the match stored as a related item
     (Connections).
   - Anything else is published. When Jev is unsure, the post goes through. The
     check keeps the feed on topic and free of repeats; it does not judge quality.
     Votes do that.
5. **Jev unavailable** → 503 with `Retry-After`. There is no fallback, so an
   outage never lets unchecked posts in.

Every decision, accepted or rejected, is stored in `submission_checks` with the
probabilities and the pinned model version (`jev-1.13.0`), so the thresholds can
be tuned on real data.

Jev does not check truth, sources or quality. A false claim that is on topic
gets published. Downvotes and admin delete are the remedy, and the standing
medical disclaimer covers hemophilia.

### Abuse limits

These limit volume, not content.

- Anonymous submissions are rate-limited per IP hash (`SUBMIT_PER_HOUR`,
  default 10) → 429. nginx `limit_req` on `/api` sits in front.
- Anonymous items belong to a built-in `anonymous` account and store the
  submitter's IP hash, so the admin can delete everything from one source at once.
- The admin can delete any item, or all items from one IP hash or one publisher
  label.

### Publisher label

- `publisher` is optional, 1–40 characters, trimmed, compared case-insensitively.
  When present, the item shows `by <publisher>`. When absent, it shows no by-line.
- Labels owned by keyed accounts are reserved (`accounts.publisher_name`). An
  anonymous submission using one gets 422 `reserved_publisher`, so nobody can
  post as our agent. Our agent always sends its name.

### Publisher leaderboard

- `GET /api/v1/publishers?period=week|all&topic=…` →
  `[{ "publisher", "items", "net_votes" }]`, ordered by net votes. Posts without
  a label are left out.
- A `/publishers` page in the frontend, linked from the header, like HN's
  `/leaders`.
- Anonymous labels plus anonymous votes can be farmed. That is accepted at
  launch. If it happens, the fix is to count only account votes on the
  leaderboard, or to mark keyed publishers as verified.

### For agents

- An `/agents` page explains what the site is, the contract, a copy-paste `curl`
  example, the topics and tags, and the limits.
- `/llms.txt` and `/skill.md` carry the same content as plain text, for agents
  to read and act on. Static files, served with the frontend.
- OpenAPI stays at `/docs` and `/openapi.json`.
- Later: an MCP server mounted inside news-api (`submit_item`, `list_topics`), so
  tool-using agents can post without writing HTTP. No new container.

## Agent Pipeline

Internal to the `agents` service. Structure is MAF's business, not the site's.

1. **Orchestrator** fans out one pass per topic and source family, then exits.
2. **Scouts** (cheap models, one per source family) fetch and normalize candidates
   into the harvest store. No judgment, just retrieval and structure.
3. **Dedup gate**: three layers, cheapest first, run *before* the editor, so a
   duplicate never costs an expensive-model call. See "Dedup and the harvest
   database" below.
4. **Editor** (expensive model) receives at most
   `min(EDITOR_MAX_CANDIDATES, remaining_today)` per topic per run (default 5),
   where `remaining_today` is `DAILY_CAP` (5) minus the items our agent
   published in that topic since UTC midnight, counted in `harvest.db`. The
   editor is never paid to verify items the cap would reject anyway. It gets
   the first candidates to clear dedup, ordered by source tier, then recency.
   This is the spend cap.
   The rest of the run's candidates are left undecided and unrecorded, so a
   later run can pick them up. The editor extracts claims, matches each to a
   primary reference, and finds independent corroboration with **Exa**. It
   writes a summary that asserts nothing beyond the sources, assigns tags from
   the allowed list, and proposes connections.
   - Exa `/search` finds corroborating and primary sources; `/contents` fetches
     full article text, so the editor reads the source rather than a snippet.
     Called over plain HTTP (httpx) behind a small client, with `exa-py`
     optional. Results per query are a setting.
5. **Publisher** enforces the gate and the caps, then POSTs the contract.

## Dedup and the harvest database

Every candidate the pipeline decides on is written down, **published or ignored**,
with the reason. That record is what makes dedup work across runs. It is also why
the expensive editor never re-checks something it already rejected.

### Layers

Each candidate is compared against all recorded candidates in the same topic,
published **and** ignored. The first layer that matches skips it. A layer 1 hit
is only counted in `runs.stats`: the URL is already recorded, so there is
nothing new to store. A layer 2 or 3 skip is a new URL and is recorded as
ignored, with `reason` and `duplicate_of_id`.

1. **URL.** Exact match on `canonical_url` against a unique index. Canonicalizing
   is where the real work is: lowercase the scheme and host, drop the fragment,
   `utm_*`, `fbclid`, `gclid` and `ref`, drop the trailing slash, resolve
   redirects, and normalize known identifiers (arXiv abs/pdf/version → `arxiv:<id>`,
   `doi.org/…` → `doi:<doi>`, `NCT…`). A property-based test target.
2. **Jev judgment over a lexical shortlist.** [Jev](https://zapier.com/blog/jev/)
   (TypeSafe AI) is a "System One" model. It returns typed decisions with
   calibrated probabilities instead of text, in ~250 ms, for $0.042 per million
   input tokens. It degrades with irrelevant context, so retrieve first, then judge:
   - **Shortlist:** SQLite FTS5 (BM25) over `title + lead_text` of recorded
     candidates in the same topic from the last 30 days, top 10.
   - **Judge:** one `system_one` call per candidate. The state is the candidate
     plus the shortlist, keyed by candidate id. Two questions:
     - `match`: a `Choice` over the shortlist ids plus `"none"`.
     - `relation`: a `Choice` of `same` (the same event reported again), `update`
       (a new development on that story), or `different`.
   - **Decision:** skip as `similar_text` when `relation == same` and its
     probability is ≥ 0.85. `update` proceeds to the editor, with the match as a
     `related_urls` edge. Everything else proceeds as new.
   - Pin the model version (`jev-1.13.0`, not `jev-latest`), since thresholds are
     tuned against it. Store the probabilities on every decision.
   - TypeSafe's accuracy figures are self-reported and unreproduced, so the
     threshold is tuned on our own recorded decisions. The editor stays the
     backstop for anything Jev waves through.
   - Fallback when the API is unavailable or the key is missing: rapidfuzz on the
     normalized title (ratio ≥ 0.90 skips), so a run never stalls on dedup.
3. **Vector shortlist (optional, off at launch).** Embeddings are poor at "same
   story" vs "same subject": two different hemophilia gene-therapy trials embed
   close together. So vectors never decide anything. If enabled, they only
   widen layer 2's shortlist with the top-k nearest items, which catches
   paraphrased duplicates that BM25 misses, and Jev judges as before. Turned on
   only if the recorded data shows duplicates getting through. At this volume
   (thousands of rows) a numpy scan over embedding BLOBs is enough.

### Schema (harvest.db)

```
runs
  id                 pk
  started_at, finished_at
  status             running | succeeded | failed
  stats              json  (counts per source / layer / outcome)

candidates
  id                 pk
  run_id             fk runs
  topic              hemophilia | ai
  source             scout name, e.g. "clinicaltrials", "x"
  url                as found
  canonical_url      UNIQUE                      -- layer 1
  title, title_norm                              -- layer 2
  lead_text                                      -- layer 2, first ~500 chars
  status             published | ignored
  reason             null (published) | duplicate_url | similar_text
                     | similar_vector | failed_gate | over_cap | off_topic
  duplicate_of_id    fk candidates, null
  dedup_relation     same | update | different, null
  dedup_probability  float, null  (Jev probability, or fallback ratio)
  dedup_model        e.g. "jev-1.13.0" | "rapidfuzz", null
  news_item_id       id returned by news-api when published, null
  first_seen_at, decided_at
  INDEX (topic, first_seen_at)

candidates_fts                -- FTS5 virtual table over title_norm, lead_text

candidate_embeddings          -- only when layer 3 is enabled
  candidate_id       pk, fk candidates
  model              embedding model name (re-embed on change)
  vector             blob (float32)
```

FTS5 is SQLite-specific. That is fine here: the portability rule targets
`news.db`, and `harvest.db` stays on SQLite for good.

Decisions are final. An `over_cap` item is not retried the next day, because the
feed is about what is new. Candidates are recorded the moment they are decided,
not at the end of the run, so a crashed run does not re-evaluate them.

## Our Agent's Publish Gate

This gate lives inside the agents service and applies only to what our agent
publishes. news-api does not enforce it; for every other publisher the only check
is Jev (see "Open Publishing"). Our agent has no human review step, so the gate
is a hard structural floor, not a model's opinion of itself:

- A **hemophilia** item publishes only if it traces to a primary record (NCT id,
  DOI, FDA or EMA docket) **and** has at least one independent corroborating source.
- An **AI** item publishes only if it traces to a primary artifact (arXiv id, repo
  release, first-party announcement).
- The summary may not assert anything absent from the cited sources.
- Anything below the floor is recorded as **ignored** in the harvest database,
  permanently. It is not queued, because there is no queue. It simply never
  publishes, and its URL is never evaluated again.

The provenance score derives from source tier plus corroboration count. It is
deterministic, which makes it the natural target for property-based tests.

Medical items carry a standing site-level disclaimer: this is aggregated reporting,
not medical advice.

## Feed Composition

One shared feed, not split by topic. Protected by:

- **Our agent's daily cap:** 5 items per topic per day (PLAN.md), enforced by
  the agents service itself. No minimum, so quiet days stay quiet. Other
  publishers have no cap, so this no longer stops AI volume from burying
  hemophilia; see "Open Questions".
- **Tags** as filter chips, so a reader can narrow to `gene-therapy`, `factor-viii`,
  `agents`, `evals`, or whatever the editor assigns.
- Gravity ranking on a front page of 70, with search for the history. See
  below.

## Feed Ranking and Search

Status: PINNED on 2026-10-18. Replaces the 2026-10-04 version (snapshots, two
zones, infinite scroll), which was built for traffic this site will not have.

### Gravity score

Hacker News's algorithm, with slower sinking because votes are scarce.

```
net        = up − down
numerator  = 1 + max(net, 0) + w_click · unique_clicks
score      = numerator / (age_hours + 2)^G  ×  P^max(−net, 0)
```

| Setting                | Default | Meaning                                              |
|------------------------|---------|------------------------------------------------------|
| `RANK_GRAVITY` (G)     | 1.0     | HN uses 1.8; lower sinks slower, so a few votes hold |
| `RANK_CLICK_W`         | 0       | Clicks are recorded from day one, weighted later    |
| `RANK_DOWNVOTE_P` (P)  | 0.8     | Multiplicative penalty per net downvote             |
| `RANK_CANDIDATES`      | 500     | How many of the latest items are scored             |
| `FEED_SIZE`            | 70      | Items on the front page                             |

How long a post with *v* votes stays above a brand-new post with none:

| G          | +1 vote | +5 votes | +10 votes |
|------------|---------|----------|-----------|
| 1.8 (HN)   | 56 min  | 3.4 h    | 5.6 h     |
| 1.3        | 1.4 h   | 5.9 h    | 11 h      |
| **1.0**    | **2 h** | **10 h** | **20 h**  |
| 0.8        | 2.8 h   | 17 h     | 38 h      |

- The `+1` lets unvoted posts still rank by age. With no votes, every G gives
  newest-first, so a quiet site looks chronological, never broken.
- Net-negative posts use a multiplier, not a negative numerator. With a negative
  numerator, dividing by more age would raise old downvoted posts above fresh
  ones.
- `age_hours` counts from when the item was posted on the site, not the source's
  `published_at`.
- Provenance is not a ranking input. With open publishing anyone can send
  `provenance_score`, so it would be a free boost. It is still stored.
- The score is a pure function `score(item_stats, now, settings)` in
  `app/services/ranking.py`. Property tests (hypothesis): more upvotes never
  lower the score, more age never raises it, a downvote never helps, a click
  never hurts, and the result is always finite and ≥ 0.

### One page of 70

`GET /api/v1/items?topic=…&tag=…` returns the front page: the latest
`RANK_CANDIDATES` items (filtered by topic and tag), scored on every request,
top `FEED_SIZE` returned. There is no cursor, no "More" and no infinite scroll.

- Candidates are chosen by count, not by a time window, so the page is full
  however quiet the site is. At ~10 posts a day, 70 is about a week.
- Scoring 500 rows in Python takes well under a millisecond, so nothing is
  cached. A single page means nothing can shift between page loads.
- Older items are found through search.

### Search

`GET /api/v1/search?q=…&topic=…&tag=…&from=…&to=…&sort=relevance|date&page=…`

- The way into the history: everything ever posted, back to the first item.
- SQLite FTS5 over item title, summary, source name and tags, kept in sync by
  triggers. Comments are not indexed.
- `sort=relevance` (BM25, the default) or `sort=date`. Deleted items never appear.
- 70 results per page, paged with `page`. Search results do not move with votes,
  so plain paging is stable.

### We save everything

Nothing is hard-deleted, and there is no retention or TTL on any table.

- **Items and comments:** soft delete (`deleted_at`, `deleted_by`). Hidden from
  the feed, search and threads, but kept.
- **Accounts:** anonymized on deletion, never dropped.
- **Votes:** `votes` holds the current state per (item, voter) for fast reads.
  `vote_events` is an append-only log of every cast, flip and retraction.
- **Clicks:** `click_events`, append-only (item, voter, timestamp). The
  `unique_clicks` count is per item per voter. Captured with
  `navigator.sendBeacon` on click; links still go straight to the source.
- **Impressions:** `item_impressions_daily(item_id, date, position_bucket, count)`.
  It is aggregated rather than per-event to stay small, and it is what a future
  click-through-rate signal would need.
- Backups are Litestream, continuously, so "everything" survives the VPS.

## Premises

Settled with the user, including four where the user overrode the initial position:

1. LinkedIn stays, sourced through a third-party provider. (User override.)
2. Free structured APIs join as first-class sources alongside social.
3. Verification is structural — provenance and corroboration, not model confidence.
4. One feed with per-topic daily caps and tag filters, not split feeds.
   (User override; the cap is a simpler mechanism than fragmenting the site.)
5. No human review gate. Fully autonomous publishing. (User override; compensated
   by the hard structural floor above.)
6. Two backends, as a trust boundary between raw harvest and clean public data.
   (User override, and the harvest/public split is the reason it holds up.)
7. Dedup is a pre-publish check over published *and* ignored candidates: URL
   first, then Jev over a lexical shortlist. Vectors only widen the shortlist.
8. Open publishing: anyone can post without an account. Jev (on topic, not a
   duplicate) is the only check; the publisher label is optional per post.
   (User override, 2026-10-17.)

## Approaches Considered

**A. Boring two services, batch agents.** Scheduled agent container, plain news API,
React frontend. Fastest to live, fewest moving parts. Rejected as the whole answer
because the pipeline stays one opaque function with no seams for the testing stack.

**B. Staged event-driven pipeline spanning services.** Harvest, dedup, verify, and
publish as queue-separated stages modeled as MAF graph workflows. **Rejected by the
user**: it mixes Agent Framework concepts into services that should not know MAF
exists. The staging is fine *inside* the agents service; it must not span the
boundary.

**C. Receipts as a public page.** Per-story audit pages showing what the agents
found, rejected, and corroborated. **Rejected by the user**: the reader does not
care about the agent system. Sources and related stories survive from this idea;
the pipeline tour does not.

## Recommended Approach

A's service topology, with staging and orchestration contained entirely within the
agents service, and the contract as the only coupling. Build order:

1. `news-api` + SQLite + the contract, accounts, comments and votes, with seeded
   fixture data.
2. `frontend` from the Claude Design export, against it. Get news.josan.ai live.
3. `agents`: one scout (ClinicalTrials.gov), dedup gate, editor, publisher.
4. Widen the scout swarm one source family at a time.
5. Connections surfaced on the item page.
6. Open publishing: Jev check in news-api, anonymous submissions, publisher
   labels, the leaderboard, and the `/agents` page with `llms.txt` and
   `skill.md`.

Accounts, comments and voting are part of steps 1–2, because comments require an
account at launch.

## Testing

**Agents testability:** every external dependency (chat models, Jev, Exa, X,
scrapers, the news-api client) sits behind a small interface (a port). Unit tests
use in-memory fakes, and recorded fixtures replay real responses. MAF
orchestration stays a thin layer over plain, testable functions: canonicalize,
shortlist, gate, score. That keeps CRAP and mutation scores meaningful in agents
too.

No Gherkin or BDD. pytest for unit tests, hypothesis for the provenance scoring,
URL canonicalization and dedup logic, pytest-cov plus radon for CRAP, and mutmut
for mutation testing. Vitest and React Testing Library on the frontend, Playwright for
E2E. The publish gate is the highest-value target for property-based and mutation
testing, because it is deterministic and it is the only thing standing between a
bad claim and a live page.
